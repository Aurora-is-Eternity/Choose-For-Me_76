# 分支管理实践：四次真实的合并，其中一次冲突

本文记录本项目从 v1.0.0 到 v1.1.0 期间真实发生的分支创建、合并与冲突解决。
所有提交号都能用 `git log --graph --all` 复核。

## 为什么单人项目也要开分支

直接往 `main` 推也能跑，但会丢掉三样东西：

1. **改动的边界**：一次提交里混了「修 bug」和「加选项」，出问题时没法只回滚其中一个；
2. **可评审性**：评审人需要看到一个意图单一的 diff；
3. **可回退性**：发布出问题时，能确定「哪一批改动」需要撤回。

所以即使只有一个人，也按「一个意图 = 一个分支 = 一次 `--no-ff` 合并」执行。

## 采用的模型

轻量 GitHub Flow（不用 `develop` 长期分支）：

| 分支 | 用途 | 合入方式 | 合并后 |
| --- | --- | --- | --- |
| `main` | 随时可用、随时可发布，受保护 | — | 长期存在 |
| `feat/*` | 新功能、新场景、新选项 | `git merge --no-ff` | 保留（评审期便于复核） |
| `fix/*` | 缺陷修复 | 同上 | 同上 |
| `docs/*` | 纯文档 | 同上 | 同上 |

## 案例一：一个「只在别人手机上出现」的 bug

**症状**：同学从群里点开分享链接，页面一片空白——转盘、场景标签、历史记录全都没有。
本地测试一切正常。

**定位**：`src/core.js` 的 `decodeHash`：

```js
const parsed = JSON.parse(decodeURIComponent(raw));
```

聊天软件经常把长链接截断，留下 `#%E0%A4%A` 这种半截百分号编码。
`decodeURIComponent` 直接抛 `URIError`，而这个函数在 `boot()` 里是同步调用的，
异常冒出去之后后面的渲染代码一行都没执行——于是白屏。

**修复**（`8c5095b`）：

```js
let parsed;
try {
  parsed = JSON.parse(decodeURIComponent(raw));
} catch (err) {
  return [];   // 降级成「没有选项」，回退到默认场景
}
```

同时补了三个用例：截断的编码、非数组 JSON、字符串 JSON。

**教训**：**凡是「来自外部的字符串」都必须假设它是坏的。**
链接、粘贴板、`localStorage`、URL 参数——这四类输入在本项目里都做了兜底，
只有 hash 这一处最初漏了，而它恰好是最容易被别人改坏的地方。

## 案例二：两个分支同时给「吃什么」加菜（真实冲突）

这是本次演练的核心。

### 分支 A：`feat/options-hotpot`

```diff
-      options: ['吃食堂', '点外卖', '下馆子', '自己做饭', '泡面加蛋', '沙拉轻食'],
+      options: ['吃食堂', '点外卖', '下馆子', '自己做饭', '泡面加蛋', '沙拉轻食', '火锅', '烤肉'],
```

理由：宿舍群里「火锅」「烤肉」的呼声最高，先放进默认菜单。

### 分支 B：`feat/options-late`

```diff
-      options: ['吃食堂', '点外卖', '下馆子', '自己做饭', '泡面加蛋', '沙拉轻食'],
+      options: ['吃食堂', '点外卖', '下馆子', '自己做饭', '泡面加蛋', '沙拉轻食', '麻辣烫', '烧烤'],
```

理由：麻辣烫和烧烤是「夜里也不一定要吃宵夜」的正餐选项。

### 制造冲突

两个分支都从 `0bb3993` 出发，改的是**同一行**：

```bash
git switch main
git merge --no-ff feat/options-hotpot
# Merge made by the 'ort' strategy.

git merge --no-ff feat/options-late
# Auto-merging src/core.js
# CONFLICT (content): Merge conflict in src/core.js
# Automatic merge failed; fix conflicts and then commit the result.

git status --short
# UU src/core.js
```

### 冲突现场

```text
<<<<<<< HEAD
      options: ['吃食堂', '点外卖', '下馆子', '自己做饭', '泡面加蛋', '沙拉轻食', '火锅', '烤肉'],
=======
      options: ['吃食堂', '点外卖', '下馆子', '自己做饭', '泡面加蛋', '沙拉轻食', '麻辣烫', '烧烤'],
>>>>>>> feat/options-late
```

### 为什么不是二选一

因为两个意图**并不互斥**：A 想覆盖「想吃好的」，B 想覆盖「夜里也想吃的重口味」，
四者可以同时存在。真正的约束只有一个——不能超过 `MAX_OPTIONS`（24）导致静默截断。

解决结果：

```js
options: ['吃食堂', '点外卖', '下馆子', '自己做饭', '泡面加蛋', '沙拉轻食', '火锅', '烤肉', '麻辣烫', '烧烤'],
```

选项从 6 条变成 10 条，仍在 24 上限内；合并后立刻跑 `npm test`，
用例会检查「场景选项本身也是干净的（无重复、无空串）」，这道断言就是这次合并的兜底。

合并提交 `42449f7` 的正文里写清了「为什么不取舍」：

> 两个分支的意图都是「让默认菜单更像宿舍真实语境」，没有互斥的理由，
> 所以没有取舍的必要——只需要确认合并后 `parseOptions` 的清洗与去重仍然成立。

**教训**：冲突不是错误，是信息。它告诉你两个改动在同一处上下文里表达了不同意图，
需要人来做判断；而判断的依据是读两条提交信息，不是看谁的 diff 更长。

## 案例三：加场景时顺手改坏过什么

`feat/scene-night` 只动了 `DEFAULT_SCENES`，加了一个 `nights` 场景。
看起来无害，但测试里有三条结构性断言会兜住它：

- 每个场景至少 5 个选项；
- 场景 id 不重复；
- 选项本身经过 `parseOptions` 不发生任何变化（说明没有重复项）。

这类「数据结构断言」比「断言场景数量等于 4」更耐用——
后者会在每次加场景时假失败，前者只在真的破坏约定时才失败。

## 案例四：需求边界上的那次犹豫

`feat/a11y-keyboard` 加的是空格/回车开转。写之前先问了一个问题：
**这算无障碍改进，还是又一个功能？**

判断标准是「删掉它会不会让某类用户无法使用」：只用键盘的人确实无法触发转盘，
所以它属于前者。于是实现时也守了两条边界：

- 输入框里打字不能被劫持（`event.target.tagName` 判断）；
- 不去抢按钮自己会处理的空格（这就是 `docs/issue草案.md` 第 5 条记录的遗留问题）。

## 合并策略：为什么坚持 `--no-ff`

| 策略 | 历史形态 | 适用 | 本项目选择 |
| --- | --- | --- | --- |
| 直接推 `main` | 线性 | 单人实验 | ❌ |
| `--ff` 快进合并 | 看不出分支 | 分支只有 1 个提交且无意义 | ❌ |
| `--no-ff` | 保留合并节点 | 需要「哪批改动一起合入」的信息 | ✅ |
| `squash` | 压成 1 个提交 | 分支提交很碎、无需保留演进 | ❌ |

`--no-ff` 的代价是历史多一个节点，收益是 `git log --first-parent` 能直接看到「每次合入」的清单，
`git revert -m 1 <merge>` 能整批撤回。

## 分支清理与标签

```bash
# 真实项目应当在合并后立即删除分支：
git branch -d feat/scene-night feat/options-hotpot feat/options-late

# 发布点打附注标签（带说明，而不是轻量标签）
git tag -a v1.1.0 -m 'v1.1.0：宵夜场景、键盘操作、坏链接白屏修复'
git push origin main --tags
```

> 本仓库在课程评审期内**保留**了已合并的分支，方便评审人用 `/branches` 与 `/network` 复核；
> 这是「证据」与「卫生」之间的一次有意取舍。

## 复现命令

```bash
git log --graph --oneline --all --decorate   # 全部分支历史
git show 42449f7                             # 冲突解决提交
git show 42449f7 -- src/core.js              # 只看最终选项
git rev-list --merges --count HEAD           # 合并提交数
git log --first-parent --oneline             # 每次合入的清单
```

## 从这四次合并里学到的四件事

1. **意图单一的提交，冲突也小**：正因为每个分支只干一件事，冲突才只集中在一行；
2. **合并前先读提交信息，再读 diff**：diff 说「改了什么」，提交信息说「为什么改」；
3. **冲突解决要用测试兜底**：解决完先跑测试，比肉眼检查可靠；
4. **数据结构断言比数量断言耐用**：后者会在正常演进中假失败，前者只在破坏约定时失败。
